# U²-Netp 分割模型说明与移动端负载评估

## 1. 当前模型与用途

项目实际使用的是 **U²-Netp ONNX**，属于通用显著物体检测（Salient Object Detection，SOD）模型，不是语义分割、人像专用 matting，也不是带点选／框选提示的基础大模型。

- 文件：`src/assets/models/u2netp.onnx`
- 文件大小：4,574,861 字节，约 4.57 MB（4.36 MiB）
- SHA-256：`309c8469258dda742793dce0ebea8e6dd393174f89934733ecc8b14c76f4ddd8`
- 参数量：约 110 万量级；本文不把模型文件大小等同于精确参数量
- 权重精度：当前分发模型按 FP32 张量运行
- 运行依赖：ONNX Runtime，不需要 PyTorch
- 桌面后端：CPU、DirectML；代码同时支持可选 CUDA
- 上游结构：<https://github.com/xuebinqin/U-2-Net>
- 论文：<https://arxiv.org/abs/2005.09007>
- ONNX 分发来源与许可证：见 `src/assets/models/README.md`

它回答的问题是“画面中最显著的主体在哪里”。输出经后处理变成 0／255 二值 Mask，再由现有涂抹、GrabCut 和形态学工具继续修正。

## 2. 原理与架构

### 2.1 两层嵌套 U 结构

U²-Net 的核心是 **U-Net 内再嵌套小型 U-Net**：

1. 外层是六阶段编码器、六阶段最深语义特征和五阶段解码器，通过跳跃连接把浅层边缘与深层语义结合起来。
2. 每个阶段使用 RSU（ReSidual U-block）。RSU 内部先下采样获取多尺度上下文，再上采样恢复分辨率，并以残差方式保留原特征。
3. 深层 RSU-4F 使用空洞卷积代替继续下采样，在扩大感受野的同时减少分辨率损失。
4. 六个阶段各产生一张侧向显著图，再融合成主输出。训练时深监督这些侧输出，推理时项目只取第一个融合输出 `d0`。

U²-Netp 是缩减通道后的轻量版：各主要阶段输出通道为 64，RSU 中间通道为 16；完整版会显著增加通道和权重。

| 部分 | 结构 |
|---|---|
| 编码器 | RSU-7 → RSU-6 → RSU-5 → RSU-4 → RSU-4F → RSU-4F |
| 解码器 | RSU-4F → RSU-4 → RSU-5 → RSU-6 → RSU-7 |
| 跳跃连接 | 对应尺度特征拼接后解码 |
| 侧输出 | 6 张显著图，上采样到 320×320 |
| 融合输出 | 6 张侧输出拼接后用 1×1 卷积融合，并经 sigmoid |

### 2.2 为什么适合当前桌面端

- 权重只有约 4.57 MB，适合随应用本地分发。
- 固定 320×320 输入，计算量不随原照片像素数线性增长。
- 对人物、玩具、手工作品等“明显主体”比传统阈值法更有通用性。
- 输出是整图 Mask，能直接进入当前图纸生成和 BOM 排除背景流程。

限制也很明确：它不是交互式抠图大模型，不保证多主体全保留，也不保证头发丝、透明物、低对比边缘、阴影和复杂背景的精细 alpha。当前产品仍应保留手动修正入口。

## 3. 输入规定

实际 ONNX 输入已从本地模型读取确认：

| 项目 | 规定 |
|---|---|
| 输入名 | `input.1` |
| 形状 | `1×3×320×320`，NCHW |
| 类型 | `tensor(float)`，FP32 |
| 通道 | RGB，不是 OpenCV 默认 BGR |
| 缩放 | 任意尺寸 RGB 图直接缩放至 320×320；不保持长宽比、不 padding |
| 数值 | 先归一化到 `[0,1]` |
| 标准化 | mean=`[0.485,0.456,0.406]`，std=`[0.229,0.224,0.225]` |

输入张量本身约占 1.17 MiB。原图较小时也会放大到 320×320；原图较大时，网络主体计算仍固定，但原图读取及 Mask 还原会增加内存和后处理成本。

## 4. 输出与后处理规定

实际 ONNX 有 **7 个输出**，输出名为 `1959`～`1965`，每个都是：

```text
1×1×320×320，FP32，sigmoid 显著性分数图
```

项目后处理顺序：

1. 取第一个融合输出。
2. 对整图做安全 min-max 归一化；极差小于 `1e-8` 时返回全零，避免 NaN。
3. 双线性插值恢复到原图宽高。
4. 按阈值二值化：大于等于阈值的位置为 255，其余为 0。
5. 返回单通道 `uint8` Mask，与原图高宽一致。

阈值是**应用后处理参数**，不是神经网络训练参数。内部阈值 `T∈[0,1]` 默认 0.5；若界面使用“前景强度” `S`，则映射为 `T=1-S`，保证强度越大保留前景越多。阈值越低保留越多，但更容易带入背景；越高越保守，但更容易吃掉边缘。

单张输出约 0.39 MiB，7 张约 2.73 MiB；实际峰值内存还包括中间激活、运行时、会话、原图和缩放缓存，不能只按模型和输出张量估算。

## 5. 桌面性能实测

测试环境：

- CPU：Intel Core i9-14900HX
- GPU：NVIDIA GeForce RTX 4060 Laptop GPU
- 内存：31.8 GB
- ONNX Runtime：1.24.4（DirectML 构建）
- 图片：固定 1280×720 合成图
- 统计：冷启动 1 次；预热 3 次后测量 12 次
- 计时范围：预处理＋推理＋Mask 还原，冷启动还包含会话初始化

| 后端 | 冷启动 | 预热均值 | 预热中位数 | 预热 P95 | 前景像素 |
|---|---:|---:|---:|---:|---:|
| CPU | 343.42 ms | 73.98 ms | 71.69 ms | 85.67 ms | 274,664 |
| DirectML | 933.69 ms | 15.00 ms | 15.02 ms | 16.49 ms | 274,664 |

结论：

- 当前桌面 CPU 已能达到可交互的单次分割速度。
- DirectML 预热后更快，但首次初始化明显慢于 CPU，因此应避免反复创建会话。
- 两种后端本次输出的前景像素数一致。
- CUDA 路径尚未在匹配的 ONNX Runtime GPU／CUDA／cuDNN 环境中实测。
- 合成图结果只用于性能与一致性检查，不代表真实素材分割质量，也不是其他机器的性能承诺。

复现命令：

```powershell
.\.venv\Scripts\python tools\benchmark_u2netp.py --provider cpu
.\.venv\Scripts\python tools\benchmark_u2netp.py --provider directml
.\.venv\Scripts\python tools\benchmark_u2netp.py --provider cpu --image "D:\path\photo.jpg"
```

## 6. 移动端大致负载判断

移动端目前**没有接入该模型，也没有真机跑分**。以下是工程估算，不是实测承诺。

### 6.1 有利因素

- 模型文件本身只有 4.57 MB，网络输入固定为 320×320。
- 单次按需运行比实时相机分割容易控制负载。
- 可以在用户点击后懒加载，并复用一个会话，避免每次初始化。
- CPU／XNNPACK 可作为第一版基线，不必一开始引入复杂 GPU 代理。

### 6.2 主要成本

- ONNX Runtime Mobile 原生库会增加 APK／ABI 体积，具体增量必须按构建产物测量。
- 中间激活和运行时内存明显高于 4.57 MB 权重；应用已有 Flutter、图片和 OpenCV 内存，叠加后更需关注峰值 RSS。
- 低端 CPU、限频和高温会放大尾延迟；冷启动通常会明显高于预热推理。
- 网络虽固定输入，最终 Mask 仍要恢复到原图尺寸，大图后处理不能忽略。

### 6.3 预估区间

假设使用 ONNX Runtime Mobile、CPU／XNNPACK、2～4 线程、会话复用：

| 设备类别 | 单次预热耗时粗估 | 说明 |
|---|---:|---|
| 近年中端安卓 | 约 150～600 ms | 有机会达到可接受的按需交互 |
| 较旧或低端安卓 | 约 0.6～2 s | 必须后台执行并显示进度 |
| 冷启动 | 可能额外增加数百毫秒至数秒 | 取决于运行时、加载和设备 |

这些区间只用于决定“是否值得做真机 spike”，不能写成发布指标。增量内存建议先把 **150 MB 以内**作为验收目标；若接近或超过 250 MB，应优先做运行时裁剪、线程与内存复用优化，而不是直接上线。

## 7. 移动端验证顺序与准入门槛

建议先做 **ORT Mobile CPU／XNNPACK spike**，不要同时接入多个后端：

1. 单 ABI 集成，记录 APK 增量、模型加载和首次推理成本。
2. 所有推理放到原生后台线程／isolate，主 isolate 不做同步等待。
3. 会话懒加载并复用，限制并发为 1，避免连续点击创建多个会话。
4. 中端与低端至少各一台真机，记录冷启动、P50、P95、峰值 RSS、温升和耗电。
5. 与桌面相同输入及阈值对比 Mask IoU，同时用真实素材人工检查边缘。
6. 连续运行 30 次，检查内存是否持续增长、P95 是否因热降频明显恶化。

建议准入线：

- 中端机预热 P95 不高于 1.5 s，且无 ANR。
- 增量峰值 RSS 目标不高于 150 MB。
- 30 次连续运行无崩溃、无持续内存增长，后 10 次 P95 不应比前 10 次恶化超过 20%。
- 包体增量、 Mask 一致性和真实素材质量均需通过评审。

未达到门槛时，保留传统分割，不为“双端功能一致”强行上线神经分割。
